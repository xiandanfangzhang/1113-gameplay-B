# 核心玩法逻辑说明

## 1. 文档目的与适用范围

本文整理 `color-transit-demo` 当前可运行的核心对局，供程序员在任意引擎中实现同等行为。正文描述实际实现；用户已确认规则、项目文档与实现的差异列在第 11 节。本文不涉及道具、编辑器、生成器和外围系统。“逻辑步”指车辆和胜负状态的一次推进；“动画”指把已结算的球移动过程画出来。

## 2. 核心概念与玩法目标

球区是矩形格子，每格至多一颗球，也可以为空。球有颜色，目前支持红、蓝、黄、绿、橙、紫，单关可只用其中部分颜色。球区宽 1–100 格、高 1–60 格可配置；三个内置关卡使用 60×20，这不是通用玩法限制。

车库固定三列，每列从前到后最多 12 辆待发车。车有颜色和**初始容量**，表示整车最多接走多少球；当前合法值为 1 至本关球区总格数的整数。车上路后另有**剩余容量**，起初等于初始容量，每接走一球减一，不会恢复。

道路是闭合的固定路线，车辆沿路循环。路线有“球区宽度＋68”个离散**道路位置**。沿底边从左到右的前“球区宽度”个位置是接球位置，每个位置只与正上方同列的一个底排球格相邻；其余 68 个位置不接球。**道路车位**是同时允许多少辆车在路上的名额，不是一个道路位置。上限可按关设置为 1–36，缺省为 6；界面的“已上路数／上限”显示名额占用。道路位置数与道路车位上限不可混用。

玩家观察底排球色及车库列头，决定派车顺序；车辆行经底边接走同色球，球区落稳，满载车离场释放名额，再继续派车。Demo 的通关条件是球区、车库和道路全部清空。

## 3. 开局与对局流程

载入关卡或重开时，先检查配置，再复制球区和车库为本局状态。开局按第 6 节立即落球至稳定，随后计算剩余球数。道路初始为空，进度为第 0 逻辑步，派车先后顺序从头开始，未暂停，速度为 1×。开局落球没有播放动画。创建完成后立即检查胜负；例如球区与车库均为空会直接通关。

玩家可在逻辑步之间点击派车。派车本身不推进逻辑步；同一时点可连续派出多辆符合条件的车。浏览器中，若道路无车且没有待播放的落球动画，自动推进暂时停下，等待玩家操作；若有路车或落球动画，则按当前速度继续推进。

## 4. 车库与派车规则

每列只有最前面的车可以派出，同列后车被挡住。前车成功派出后从车库移除，后车立即成为列头，但不会自动派出。不同列可独立选择。若本局已通关或失败、处于暂停、所点车不在车库、不是所在列的列头、或道路已占满车位上限，派车被拒绝，状态不变。

成功派车时，车辆剩余容量设为初始容量，获得固定的出车先后顺序，占用一个道路车位，并放在循环路线尾端的一个空闲入口道路位置。同一时点连续派出的车辆占不同入口位置。派车后立即重查胜负。道路未满时，不要求路车眼下能接到球，也不要求新车颜色已在底排出现；即使暂时接不到球，仍可继续派车。道路满位时不能派车；满载车离场腾出名额后，需要玩家再次操作，系统不会自动派出车库后车。

## 5. 道路行驶与接球规则

每个逻辑步，所有路车先沿固定方向各前进一个道路位置，走过路线末端便回到起点。沿球区底边的接球段从左到右经过；未满车绕行后还会再经过底边，不因一圈没接到球而离场。

车位于接球位置、剩余容量大于零，且正上方**底排球**与车同色时，接走该球一颗。其他位置的同色球，包括被底排异色球隔住的上层球、球团左右或顶部外轮廓的球，都不能直接接走。每辆车每逻辑步至多检查当前道路位置正上方的一颗球；接球后剩余容量和球数各减一，并立即将球区完整落到稳定。刚补进这个底排格的球不会被**同一次接球事件**再次接走，须等待后续车辆或本车下一次合法行经该格。未满车保留在路上继续循环。

接球后剩余容量变成零时，车辆就在该次接球处理中满载离场，道路占用数立即减一；不等待驶完一圈或落球动画结束。

## 6. 落球与补位规则

球只能在矩形合法格内移动，不穿过其他球或边界；落球不创造、删除或变色。开局和每次接球后立即落球至稳定。落球可以跨列，但没有同排横移或额外的底排强制铺满步骤。因此，剩余球数不少于底排宽度，也不保证底排各格必满。

一颗球先试正下方，空则直落一格；否则依次试右下、左下。斜落要求斜下目标格与对应的同一行侧边格都为空，路径不能穿球。越出球区的方向不可用。左右斜下同时可用时优先右下；三个方向均不可用就暂时不动。

同一轮从下往上逐行处理，每行从左往右处理。每移动一球，立即更新原格和目标格的占用，后处理的球看到更新后的状态；每球每轮最多移动一格。重复整轮，直到完整一轮无球移动，才是逻辑稳定状态。之后再有球被接走，原先停住的球可以继续下落。画面沿这次结算记录的直落、斜落路径播放动画，逻辑格位已经在接球事件中更新到最终状态。

## 7. 对局结算的处理顺序

一个逻辑步依次发生：

1. 步数增加，到期的落球动画从播放记录移除。
2. 将本步开始时在路上的所有车各前进一步。接着按**出车先后顺序**逐辆检查接球，与车辆当前在道路上的左右位置无关。
3. 某车成功接球，立即扣除球数与该车剩余容量，并把整个球区落稳；若满载，则在处理下一辆车前立即离场、释放道路车位。后车读取前车接球和落球后的底排，所以可能接到前车触发的新补位球，也可能因底排颜色改变而接不到球。每车本步仍至多接一球。
4. 全部路车处理完后检查通关、满位死局。成功派车也会立即重查胜负。

动画是视觉回放，不阻止后续逻辑步接球，也不阻止玩家派车。动画期间路车照常移动，接球读取已落稳的逻辑球区；新的接球还可能更新正在播放的球的路径。满载离场和满足条件的通关不等待动画。道路满位死局判定则等待所有落球动画结束。暂停会冻结逻辑步与动画进度。

## 8. 通关、死局与异常状态

**通关：**球数为零、三列车库均空、道路无车，三项同时成立时立即通关。只清空球而留下待发车或未满路车，不算通关。终局后不再推进，也不能派车。

**道路满位死局：**仍有球、道路车辆数达到本关车位上限、没有正在播放的落球动画，且全部路车都无法凭自己的剩余容量接走**当前底排任意同色球**时，立即判失败。未满车会循环经过每个底边接球位置，因此这里看未来能否接到当前底排球，不要求车此刻已走到对应位置。派车使道路满位后、每逻辑步结束、动画结束后的检查都可能触发失败。失败后停止推进和派车。

**运力不足提示：**按颜色比较剩余球数与“待发同色车的初始容量＋路上同色车的剩余容量”。球数超过运力时显示缺口；这只是提示，不直接判失败，也不自动删球或补车。数量不匹配的关卡可以带着警告进入试玩。

**未判终局的停滞：**例如还有球、道路无车且车库已空；或球已清空，却仍留有待发车或未满路车。它们不满足通关，也不满足“有球且道路满位”的失败条件，当前 Demo 不另行判负。道路未满而眼下接不到球、或匹配的路车还没驶到接球位置，也不得提前判死局。

## 9. 暂停、加速与重开

暂停仅对进行中的对局生效。暂停期间车辆位置、逻辑步数、落球动画进度和胜负结算均不推进；点击派车被拒绝。恢复后从原球区、车辆位置、容量和道路占用继续。

速度可在 1×、2×、4× 间切换，改变现实时间内推进逻辑步及动画播放的快慢，不改变每步行驶距离、接球次数、落球顺序、容量扣除或胜负条件。相同逻辑步和相同派车时点的结果应相同。

重开从当前选定的关卡配置重新创建一局，重新执行开局落球；球、车库、路车、步数、胜负、暂停和加速都回到开局状态。重开后速度为 1×、未暂停；暂停或终局后也可重开。即时试玩中，重开使用当前编辑草稿，不改写草稿。

## 10. 关键边界案例与验收示例

- **隔球：**初始情况为已落稳的球区中，某列底排是蓝球、其上方的红球被挡住；红车经过该列。预期结果为红车不隔着蓝球接红球，容量不变。
- **同次不连吸：**初始情况为同列底排和上一格都是红球，红车还剩两格容量。红车经过该列时，只接走原底排球，容量减一；上方红球逻辑上补到底排，但本次事件不再被该车接走。
- **落球方向：**正下方空、斜下也空时直落；正下方堵住且两侧斜向路径都通时右下；某侧同排格被占时不得从该侧斜穿。
- **同一步多车：**两辆已出车在同一步分别进入各自接球位置。预期先让两车前移，再按出车先后逐辆接球；前车使球区落稳后的底排，决定后车能否接球。各车本步至多接一球。
- **未满可派：**道路尚有名额、现有路车眼下接不到球、车库有可派列头。点击列头后仍成功占用一个道路车位，不据此判死局。
- **未到位置不判负：**道路已满，一辆未满路车的颜色出现在当前底排，但该车还在绕行段。预期继续运行，等其驶到接球位置。
- **满载离场：**道路已满，一辆车还差一颗同色球满载。接球后它在本次事件内离场并释放名额；即使落球动画仍在播放，玩家随后也可派出列头车，系统不自动派车。
- **暂停和重开：**已派车后暂停，点击车库列头被拒绝，步数、车位与车辆位置不变；恢复后继续。点击重开则回到落稳后的开局球区、原车库、空道路、第 0 步、1×且未暂停。
- **提示与剩车：**某色剩余球多于剩余运力时显示缺口，但不立刻失败；球清空后若仍有待发车或未满路车，则不通关，并提示还有车辆。

## 11. 当前实现差异与待确认项

1. **通关定义有差异。**工作区 `project.md` 记载的用户已确认核心要求是“全部球清空”；Demo 源码还要求车库和道路车辆清空。正文按 Demo 描述。若改成只按清球通关，需要确认多余车辆在通关时如何处理，本文不替其决定。
2. **“每次一批”的粒度需确认。**工作区确认规则使用“每次只接当时符合条件的一批”，没有精确定义单车一次经过可接多少颗。当前 Demo 限定为每车每逻辑步在当前道路位置正上方至多一颗，并禁止同次递归吸走补位球。若未来要让一辆车同一事件扫过多个格子，须另行确认。
3. **梯形及底排强制补满尚未实现。**工作区根 `project.md` 记录过上宽下窄及底排铺满目标，同时将含同排横移的补位方案标为待确认提案。当前 Demo 是矩形球区与普通直落、斜落，没有同排横移或铺满保证。是否改为梯形及是否允许横移仍需确认。
4. **非满位停滞没有终局判定。**当前实现只将第 8 节的满位条件判为失败，所以运力不足或球清空但留车等情况可能无法自然结束。若要增设失败或软锁处理，需要独立规则决定。

## 12. 核查依据

- `../project.md`：用户已确认的道路邻接、循环接球、落球优先级、清球要求及梯形补位提案性质；历史九关尺寸未作为通用规则。
- `project.md`、`AGENTS.md`、`README.md`：项目当前范围、默认值与文档描述；本次均对照实时源码。
- `src/constants.js`、`src/validation.js`、`src/levels.js`：颜色、尺寸、容量、道路车位的配置范围及默认值、三列车库与内置关卡。
- `src/engine.js`：开局、派车、道路行驶、接球、容量、离场、胜负、运力提示、暂停与速度状态。
- `src/gravity.js`：直落斜落条件、右侧优先、逐轮处理、稳定状态及动画路径。
- `src/main.js`、`src/render.js`：玩家操作、重开、浏览器逻辑步推进及视觉动画。
- `tests/engine.test.mjs`、`tests/gravity.test.mjs`、`tests/dimensions.test.mjs`：道路邻接、同次不连吸、车位及离场、死局等待动画、暂停加速、落球顺序、自定义尺寸及通关边界。本次先执行这三份测试文件，19 项通过；随后执行完整测试套件，44 项通过。
